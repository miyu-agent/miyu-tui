# Miyu terminal UI

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This repository is Miyu's terminal UI: the program `miyu-tui` is a full-screen terminal program that connects to Miyu's core and lets you talk to the AI in your terminal. The core lives in [miyu-agent/miyu](https://github.com/miyu-agent/miyu). This repository pins one commit of the core through a git dependency in `Cargo.toml`, and uses the core's features only through the `miyu-client` crate that the core provides.

For the launch options, keys, slash commands and settings, see [Terminal UI](https://github.com/miyu-agent/miyu/blob/main/docs/en/guide/heads/tui.md) in the manual.

## Running

This section explains how to run the terminal UI from source. Before you run it, build the core once in a checkout of the core repository:

```sh
cargo build -p miyu
```

In the commands below, replace `<core checkout>` with the path of your checkout of the core repository. Generate the model configuration with the core's `cargo xtask dev-home` (for details, see [Contributing code](https://github.com/miyu-agent/miyu/blob/main/docs/en/dev/contributing.md)); the provider address and key it writes into the configuration refer to the environment variables `MIYU_DEV_BASE_URL` and `MIYU_DEV_API_KEY`.

The first time you use a new `MIYU_HOME`, install the terminal UI's own package `tui/` from the root of this repository. The core does not ship this package, and the package is what registers the `tui.*` settings and the state directory that holds the input history. Run:

```sh
MIYU_DEV_BASE_URL=<address, up to /v1> MIYU_DEV_API_KEY=<key> MIYU_HOME=$HOME/.cache/miyu-tui-home MIYU_RESOURCES=<core checkout>/resources <core checkout>/target/debug/miyu pkg install ./tui --yes
```

`miyu pkg install` starts the core and keeps it running, and the `cargo run` below connects to that core, so this step needs the address and key as well. If you change the manifest in `tui/`, install the package again.

> The package id comes from the folder name, and the prefix of the settings keys is set by `prefix = "tui"` in the manifest. When a new version is released, the core puts this package into `packages/tui/` according to `heads.toml`.

Then run the terminal UI:

```sh
MIYU_DEV_BASE_URL=<address, up to /v1> MIYU_DEV_API_KEY=<key> MIYU_HOME=$HOME/.cache/miyu-tui-home MIYU_RESOURCES=<core checkout>/resources MIYU_CORE_BIN=<core checkout>/target/debug/miyu cargo run
```

Keep the following in mind when you run it:

- Put the environment variables in front of the command and do not `export` them, because the old version of Miyu also reads `MIYU_HOME`.
- Put `MIYU_HOME` in a directory that is not wiped, not in `/tmp`. `/tmp` is a tmpfs, so after a reboot the model configuration and session history are all lost.
- When the terminal UI starts the core, it only uses the program named by `MIYU_CORE_BIN` and does not look for `miyu` on `PATH`, because the one on `PATH` may be an old version. If the core is already running, the terminal UI can connect without this variable.

## Resuming sessions in herdr

This section explains how the terminal UI resumes sessions in herdr. `miyu-tui --resume <full session id>` resumes the given session and takes priority over `ui.startup = "recent"`.

After you create or switch the main session in herdr, the terminal UI automatically reports a resume command to herdr. When the herdr server restarts, each pane resumes its own session. Running `/new` clears the old binding. If you only quit the herdr client, the original process keeps running.

The `miyu-tui` program used for resuming must be on the `PATH` of the shell that does the resuming, and `MIYU_HOME`, `MIYU_RESOURCES` and `MIYU_CORE_BIN` must also be available. herdr does not save environment variables written temporarily in front of the original launch command, so for a trial you can write a launch script that fixes these variables and put it on `PATH`. You can try it first in a separately named herdr session, so that you do not need to stop the default server.

On Linux you can run an isolated acceptance test (herdr must be installed):

```sh
cargo test --test herdr_resume -- --ignored
```

The test uses a temporary data root, a fake model and a separate XDG configuration. It checks that two panes each resume their own session and that `/new` clears the old binding, and it does not read or write your real sessions.
